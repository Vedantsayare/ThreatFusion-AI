1. Project and Phase Overview
ThreatFusion AI is an autonomous, agentic Security Operations Center (SOC) copilot designed to triage, investigate, correlate, and apply guardrails to security events using a Neo4j knowledge graph and LangGraph agents. Upstream security telemetry originates from a Wazuh security monitoring cluster.

Purpose and scope of Phase 2
Phase 2 establishes the ingestion boundary for ThreatFusion AI. It builds an asynchronous alert poller (WazuhAlertPoller) on top of the Phase 1 WazuhClient to reliably retrieve security alerts from the Wazuh API and hand off raw, unmutated alert batches to downstream processing stages.

Implemented in Phase 2
- Asynchronous WazuhAlertPoller class in ingestion/poller.py with clean start/stop lifecycle management and async context-manager support.
- Bounded, paginated retrieval using Wazuh API conventions (offset, limit, sort, affected_items/items response shapes).
- Watermark tracking and bounded in-memory deduplication cache (default 10,000 IDs) to prevent re-ingesting previously observed alerts.
- Bounded retries with exponential backoff for transient network issues (WazuhConnectionError) and server-side errors (HTTP 5xx).
- Immediate, non-retryable failure handling for authentication errors (WazuhAuthError), TLS verification failures (WazuhTLSError), client errors (HTTP 4xx), and malformed response payloads.
- Strict concurrency control via an asyncio.Lock ensuring poll cycles never overlap or cause race conditions.
- Preserved raw alert payloads inside a typed RawAlertBatch container without loss of fidelity.
- Pydantic configuration parameters for endpoints, batch size, retry limits, and backoff delay with defense-in-depth validators.
- Comprehensive unit test suite with 20 focused tests mocking HTTP interactions without live server dependencies.

Deferred to future phases
- OCSF (Open Cybersecurity Schema Framework) normalization (Phase 3).
- Entity resolution and node/edge mapping in Neo4j knowledge graph (Phase 4).
- Event streaming via Redis Streams or Celery workers.
- Autonomous LLM multi-agent triage and investigation.
- Live integration tests against physical Wazuh VM instances.


2. Architecture and Design
The alert ingestion layer resides entirely in ingestion/poller.py. It sits logically above the Phase 1 WazuhClient and below the future normalization and correlation pipeline.

Layering and component boundaries
External Wazuh API (HTTPS port 55000)
       ^
       | HTTP Basic Auth, Bearer JWT, TLS policy, timeouts
WazuhClient (ingestion/wazuh_client.py)
       ^
       | get("/alerts", params={offset, limit, sort})
WazuhAlertPoller (ingestion/poller.py)
       |
       | RawAlertBatch(alerts=[...], count=N, watermark=T)
Downstream Handler Callback (Future Phase 3 Normalization)

Key design decisions
- Client reuse: Rather than creating another HTTP client, WazuhAlertPoller accepts an existing WazuhClient instance via dependency injection.
- Single responsibility: WazuhAlertPoller is responsible solely for ingestion reliability, pagination, deduplication, retry policy, and lifecycle. It does not parse or judge alert maliciousness.
- Overlap prevention: Alert polling occurs periodically based on WAZUH_POLL_INTERVAL_SECONDS. If a polling cycle takes longer than the interval, an asyncio.Lock ensures subsequent poll attempts exit immediately rather than spinning duplicate concurrent runs.
- Raw alert preservation: Alert dictionaries are treated as untrusted, passive JSON data and forwarded directly in raw format to prevent premature data truncation or schema loss.


3. Wazuh Alert Collection and Pagination Strategy
Wazuh exposes REST collection endpoints formatted as JSON payloads containing error codes and data blocks.

Authoritative endpoint structure
Wazuh API collections return structures formatted like:
{
  "error": 0,
  "data": {
    "affected_items": [
      {
        "id": "1697543200.12345",
        "timestamp": "2026-10-17T12:00:00.000Z",
        "rule": {"id": "5710", "level": 5, "description": "sshd brute force attempt"},
        "agent": {"id": "001", "name": "web-server-01"}
      }
    ],
    "total_affected_items": 150
  }
}

Pagination mechanics
- Polling requests supply offset, limit (controlled by WAZUH_BATCH_SIZE), and sort (+timestamp).
- The poller extracts items from data.affected_items (standard) or data.items (legacy fallback).
- Total records are read from data.total_affected_items or data.total_items.
- The pagination loop fetches pages until either:
  1. The accumulated items reach or exceed total_items reported by Wazuh.
  2. The returned page contains fewer items than requested limit.
  3. The returned page is empty.
- Malformed items inside an otherwise valid page (such as non-dict elements) are logged and skipped without crashing the ingestion cycle.


4. Deduplication and Watermark Strategy
To guarantee exactly-once delivery into the ThreatFusion AI pipeline without requiring an external database in Phase 2, the poller uses two complementary strategies:

Watermarking
- The poller tracks the highest timestamp observed across all ingested alerts.
- In subsequent polling cycles, this watermark is passed as a query parameter (e.g. timestamp_gte=watermark) to minimize redundant record queries against the Wazuh cluster.

Bounded deduplication buffer
- Even with timestamp sorting, clock skew or batched events sharing identical timestamps can cause duplicates at page boundaries.
- WazuhAlertPoller maintains an in-memory deduplication set capped at a bounded size (default 10,000 entries).
- When a new alert ID is evaluated, if it already exists in the seen set, it is discarded from the batch.
- When the seen set reaches capacity, the oldest items are evicted to keep memory consumption bounded and deterministic.
- If an alert lacks an explicit "id" or "_id" field, the poller computes a deterministic composite fallback key using SHA-256 of timestamp + rule.id + agent.id.


5. Error Handling and Retry Policy
Network communication with security infrastructure must survive transient interruptions while failing fast on permanent misconfigurations.

Transient errors (retryable)
- Network connectivity failures, socket disconnects, and timeouts raise WazuhConnectionError in WazuhClient.
- Wazuh API 5xx responses (HTTP 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout) raise WazuhAPIError with 5xx status codes.
- The poller retries these up to WAZUH_MAX_RETRIES times (default 3), applying exponential backoff: delay = WAZUH_RETRY_BACKOFF_SECONDS * (2 ^ (attempt - 1)).
- If max retries are exhausted, IngestionMaxRetriesError is raised with contextual metadata.

Fatal errors (non-retryable)
- WazuhAuthError (HTTP 401, invalid credentials, revoked token): Fails immediately without retry.
- WazuhTLSError (certificate mismatch, untrusted CA): Fails immediately without retry.
- HTTP 4xx client errors (HTTP 400 Bad Request, 403 Forbidden, 404 Not Found): Fails immediately as WazuhIngestionError.
- Schema/malformed errors (IngestionMalformedResponseError): If the Wazuh response is not a valid JSON dict or contains a non-zero error code, it aborts immediately to avoid infinite failure loops.
- asyncio.CancelledError: Never swallowed; permits cooperative shutdown during task cancellation.


6. Security and Untrusted Input Handling
Alerts originating from external agents are fundamentally untrusted input.

Threat vectors and mitigations
- Active code injection: Alert strings (rule descriptions, agent names, command logs) may contain malicious scripts or SQL injection strings. Alerts are treated strictly as passive dictionaries. No eval(), exec(), or template substitution is performed.
- Secret exposure: No passwords, tokens, or private credentials are included in logging or string representations. WazuhAlertPoller implements a safe __repr__ that reveals only the endpoint, batch size, and running status.
- Denial of Service / Memory exhaustion: Unbounded pagination could exhaust memory if a Wazuh instance returns millions of alerts. The poller limits batch size and maintains bounded deduplication buffers.
- Structured logging: All logging events use structlog with typed keyword arguments rather than string concatenation, preventing log injection.


7. Configuration and Environment Variables
Phase 2 introduces four dedicated settings to core/config.py via AppSettings:

Variable | Default | Constraints | Description
WAZUH_ALERTS_ENDPOINT | /alerts | Must start with / | Wazuh API endpoint path for retrieving alerts
WAZUH_BATCH_SIZE | 100 | 1 <= value <= 1000 | Number of alerts retrieved per pagination request
WAZUH_MAX_RETRIES | 3 | 0 <= value <= 10 | Maximum retry attempts for transient errors
WAZUH_RETRY_BACKOFF_SECONDS | 1.0 | value >= 0.01 | Base exponential backoff duration in seconds
WAZUH_POLL_INTERVAL_SECONDS | 15.0 | 5.0 <= value <= 3600.0 | Frequency of polling loop execution (from Phase 0)


8. Code Walkthrough
Key classes and methods in ingestion/poller.py:

RawAlertBatch
Dataclass holding:
- alerts: list[dict[str, Any]] (the raw, unmodified alert payloads)
- batch_size: int (number of new alerts in this batch)
- watermark: str | None (the highest timestamp ingested)
- fetched_at: float (monotonic time when batch was retrieved)

WazuhAlertPoller
Primary ingestion controller:
- __init__(client, settings, handler): Initializes poller state, sets up lock, event flags, and dedup deque.
- fetch_page(offset, limit, params): Fetches a single page with retries, exponential backoff, and schema validation.
- poll_once(): Executes a complete pagination cycle across all available pages, applies deduplication and watermarking, and invokes the registered handler callback.
- start(): Spawns the background asyncio polling loop.
- stop(): Signals the stop event, waits for any active cycle to finish, and cancels the loop task cleanly.
- __aenter__ / __aexit__: Provides context manager support for automatic start and stop.

10. Downstream Integration and Next Steps
In Phase 3, the RawAlertBatch produced by WazuhAlertPoller will be routed into the OCSF normalization pipeline:
1. WazuhAlertPoller invokes the registered handler callback with RawAlertBatch.
2. Normalization maps Wazuh rule and log schemas into OCSF Security Finding events (class 2001).
3. Validated OCSF events are forwarded to Redis Streams for durable queueing and downstream LangGraph agent consumption.

12. Glossary
- Ingestion: The process of importing and capturing raw event data from external sources into a processing pipeline.
- Watermark: A timestamp or cursor indicating the point up to which events have been observed and processed.
- Deduplication: Eliminating redundant copies of identical events to prevent duplicate downstream alerting.
- Exponential Backoff: An error-mitigation algorithm that doubles the delay between successive retry attempts to reduce load on struggling services.
- Overlap Prevention: A concurrency guard ensuring that a new scheduled job does not execute while the previous execution is still running.
- Fail-Fast: A design pattern where non-recoverable errors immediately raise exceptions rather than attempting futile retries.
- OCSF: Open Cybersecurity Schema Framework; an open standard for normalizing security event telemetry.
