1. WHAT WAS BUILT AND WHY

integrated security operations environment. It establishes two external context
integrations and a real-time investigation user interface:

1. External Threat Intelligence Integration (MISP):

     interactive human-in-the-loop approval workflow.

4. FastAPI Backend REST API:
   - Complete endpoint suite under /api/v1 (health, ingestion, investigations,
     on-demand enrichment, stats, integrations status, and approval decision).

2. MISP THREAT-INTELLIGENCE INTEGRATION ARCHITECTURE
--------------------------------------------------------------------------------
The MISP client (ingestion/misp.py) implements asynchronous HTTP querying against
MISP's /attributes/restSearch endpoint with rigorous operational and security controls:

- Safe Credential Handling:
  The MISP API key is held in memory and used strictly in Authorization headers.
  The client's __repr__ masks the API key (e.g., 'ab12***'), preventing leakage
  into debug logs, exception traces, or console dumps.

- Strict TLS Enforcement:
  TLS certificate verification is enabled by default. In production environments
  (APP_ENV=production), disabling TLS (verify_ssl=False) is rejected at both
  the AppSettings schema layer and the MISPClient constructor layer.

- Bounded Retries & Timeouts:
  HTTP requests enforce explicit timeouts (default 10s) and bounded retries
  (default 2) with exponential backoff for transient network issues (502/503/504
  or connection drops). 4xx client errors (401, 403, 404) fail immediately.

- Typed Exception Hierarchy:
  MISPError -> MISPConnectionError (MISPTLSError, MISPTimeoutError),
  MISPAuthError, MISPAPIError.

- Untrusted External Input Handling:
  All strings returned by MISP (event names, attribute values, comments, tags)
  are treated as passive untrusted data. They are never interpreted, executed,
  or rendered as raw unescaped HTML.

3. PRINCIPLE OF EXPLICIT UNCERTAINTY: MISSING INTEL != SAFE
--------------------------------------------------------------------------------
A fundamental tenet of defensive cybersecurity architecture implemented in Phase 9
is the explicit distinction between "confirmed benign" and "absence of evidence":

- When an indicator lookup in MISP returns zero matching attributes, the outcome
  is classified as MISPLookupStatus.NO_MATCH.
- Crucially, the flag `is_confirmed_safe` is set strictly to False.
- The system explicitly records an uncertainty note:
  "No matching threat intelligence found in MISP. Absence of threat intelligence
   does NOT imply the entity or indicator is benign."
- Similarly, if MISP is disabled, unreachable, or errors out, the status is
  recorded as DISABLED or ERROR, and is_confirmed_safe remains False.
- This design prevents automated systems and human analysts from suffering false
  confidence due to intelligence gaps or service outages.

4. IAM AND CMDB ASSET CONTEXT ARCHITECTURE
--------------------------------------------------------------------------------
The IAM/CMDB layer (ingestion/cmdb.py) defines a provider-neutral interface
(IAMCMDBProvider) separating organizational data models from concrete directory
implementations (Active Directory, Okta, ServiceNow, AWS Systems Manager, Snipe-IT):

- Data Models:
  * AssetContextRecord: asset_id, hostname, ip_address, owner_team, environment,
    criticality (CRITICAL, HIGH, MEDIUM, LOW, UNKNOWN), tags, source, retrieved_at.
  * IdentityContextRecord: username, full_name, email, department, status
    (ACTIVE, SUSPENDED, LOCKED, DELETED, UNKNOWN), is_privileged, source, retrieved_at.

- Principle of Non-Fabrication:
  If a hostname or username is not present in the CMDB/IAM store, the provider
  returns None. The system never invents missing attributes, default owners, or
  fictitious business criticality levels.

- Mock Provider (MockIAMCMDBProvider):
  Provides deterministic in-memory lookup by asset_id, hostname, IP address, and
  username for automated testing, development, and standalone validation.

5. NON-DESTRUCTIVE ENRICHMENT PIPELINE
--------------------------------------------------------------------------------
The EnrichmentService (ingestion/enrichment.py) orchestrates MISP and IAM/CMDB
queries without mutating the underlying security finding:

- Immutability Preservation:
  The original OCSFSecurityFinding produced in Phase 3 remains untouched.
  Enrichment data is attached as separate metadata within the investigation state
  and stored alongside the finding in the InvestigationStore.

- Safe Extraction:
  IP addresses are extracted from finding.src_endpoint and finding.dst_endpoint.
  Hostnames are extracted from finding.device. Usernames are extracted from
  finding.user.

- Graceful Degradation:
  If MISP or CMDB are offline or unconfigured, the enrichment service captures
  partial results without interrupting the investigation pipeline or failing the
  alert workflow.

--------------------------------------------------------------------------------
The frontend in dashboard/ is built with React 18, Vite 6, and TypeScript in strict
mode, styled with a custom dark-mode glassmorphism design system in Vanilla CSS:

- Component Hierarchy:
  * App.tsx: Top-level coordinator managing active investigation, filters,
    stats, and modal workflows.
  * Navbar.tsx: Brand identity, real-time integration status badges (Wazuh,
    Neo4j, MISP, CMDB), and global refresh trigger.
  * StatsBar.tsx: Overview metrics (Total alerts, Critical P1, High P2,
    Medium/Low, Pending Approvals with pulsating indicator).
  * InvestigationList.tsx: Search bar, priority filter pills (ALL, P1, P2, P3, P4),
    rich card list with priority pills, relative timestamps, host, user, MITRE tags,
    and pagination controls.
  * InvestigationDetail.tsx:
    - Full finding metadata and execution latency.
    - Deterministic triage evaluation: Rule ID, score, description, factors,
      recommended response actions, MITRE techniques.
    - External threat intelligence context: MISP matches, confidence scores,
      explicit uncertainty notice.
    - CMDB/IAM asset and identity context cards.

    approval or rejection decisions with reviewer identity and rationale notes.

- Safe Rendering & Anti-XSS:
  All user-supplied and alert telemetry data is rendered via React JSX text nodes,
  ensuring native browser HTML escaping and complete protection against script injection.

7. API ENDPOINT DESIGN AND SECURITY CONSIDERATIONS
--------------------------------------------------------------------------------
FastAPI routes under api/routes.py adhere to RESTful conventions and defensive engineering:

1. GET /health and GET /api/v1/health:
   Aggregated health status across Wazuh, Neo4j, MISP, and Guardrail services.

2. POST /api/v1/alerts/ingest:
   Ingests raw Wazuh alert, executes LangGraph workflow (Phase 7), enriches with
   MISP and CMDB context, persists to InvestigationStore, and returns 201 Created.

3. GET /api/v1/investigations:
   Bounded pagination (page, page_size le 100), filtered by priority, status, or search query.

4. GET /api/v1/investigations/{alert_id}:
   Returns full investigation detail, graph stats, guardrail decisions, and enrichment.

5. POST /api/v1/investigations/{alert_id}/enrich:
   Triggers on-demand external intelligence lookup.

6. GET /api/v1/stats:
   Aggregate metrics for SOC dashboard overview.

7. GET /api/v1/integrations/status:
   Reports integration connectivity without exposing secrets, credentials, or keys.

8. POST /api/v1/approvals/{request_id}/decide:
   Submits human approval/rejection, records decision in HashChainAuditStore, and
   updates request status.

8. HUMAN APPROVAL WORKFLOW INTEGRATION
--------------------------------------------------------------------------------
Phase 9 completes the human-in-the-loop safety architecture established in Phase 8:

- When an automated triage engine or workflow proposes high-risk containment
  (e.g., host isolation, account quarantine), the centralized GuardrailEngine
  intercepts the action and generates a cryptographic ApprovalRequest.
- The investigation detail view prominently displays a warning banner highlighting
  blocked containment actions awaiting review.
- The analyst reviews the action, rationale, and target in the ApprovalModal.
- Upon submitting 'APPROVE' or 'REJECT', the decision is validated, cryptographically
  bound to the action hash, and permanently logged to the SHA-256 hash-chain audit store.
- No containment action can execute without this cryptographic approval record.

10. SECURITY CONSIDERATIONS
--------------------------------------------------------------------------------
- Defense-in-Depth TLS: Both AppSettings and MISPClient reject unverified TLS
  when running in production.
- Secret Hygiene: API keys, passwords, and tokens are omitted from __repr__,
  excluded from API status endpoints, and protected in memory.
- Bounded Resources: In-memory store enforces max_capacity with FIFO eviction to
  prevent memory exhaustion under denial-of-service or high alert volume.
- Anti-Tampering: Human approval decisions are chained to the immutable audit store.
