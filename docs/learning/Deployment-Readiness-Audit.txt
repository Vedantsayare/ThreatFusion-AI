   mocked HTTP responses and in-memory mock providers. No live adapters exist.

CHECK 4: API Authentication, Authorization & Sensitive Endpoints
--------------------------------------------------------------------------------
Status: FAIL
Risk Level: CRITICAL
Category: API Security & Access Control

- Evidence:
  * Route Definitions (`api/routes.py`):
    - `POST /api/v1/alerts/ingest` (unauthenticated)
    - `POST /api/v1/approvals/{request_id}/decide` (unauthenticated)
    - `POST /api/v1/investigations/{alert_id}/enrich` (unauthenticated)
    - `GET /api/v1/investigations` (unauthenticated)
  * No FastAPI `Depends`, `HTTPBearer`, `APIKeyHeader`, or OAuth2 security schemes are attached to routes.
  * In `submit_approval_decision`, the `reviewer_id` is supplied arbitrarily by the client in the JSON body:
    `reviewer_id: str` (no signature, session, or token verification).

- Analysis:
  Any entity capable of sending HTTP requests to the FastAPI backend can:
  - Ingest untrusted alert data.
  - Approve or reject high-risk containment actions on behalf of any reviewer name.
  - Trigger resource-intensive enrichment workflows.
  This represents an intolerable security vulnerability for production SOC operations.

- Recommended Remediation:
  1. Implement authentication middleware (e.g., OAuth2 with OIDC/JWT, or mutual TLS + API keys).
  2. Bind approval decisions strictly to the authenticated subject (e.g., `user.sub` from verified JWT).
  3. Enforce Role-Based Access Control (RBAC): require `role: "secops-analyst"` to view investigations,
     and `role: "secops-lead"` to submit approval decisions.

CHECK 8: Audit Persistence & Fail-Closed Integrity
--------------------------------------------------------------------------------
Status: PARTIAL
Risk Level: HIGH
Category: Audit Trail & Non-Repudiation

- Evidence:
  * `guardrails/audit.py` (lines 156–160):
    `HashChainAuditStore` maintains `self._events` in-memory. File persistence only occurs if `self.log_path`
    is explicitly provided upon initialization.
  * In `api/routes.py` and `orchestrator/nodes.py`, the default `HashChainAuditStore` is instantiated without
    a persistent `log_path` or PostgreSQL backend sink.
  * If the API server or container process terminates, historical audit records in memory are permanently lost.
  * In `guardrails/engine.py`: If `audit_store.log_event()` fails, the exception aborts the evaluation,
    failing closed (PASS for fail-closed behavior, FAIL for persistence).

- Analysis:
  While cryptographic hash chaining and fail-closed evaluation are implemented correctly,
  audit durability across container restarts is not configured by default.

- Recommended Remediation:
  1. Mandate a durable PostgreSQL or append-only write-once-read-many (WORM) storage backend for `HashChainAuditStore`.
  2. Add startup health checks that verify the audit store is writable before accepting alerts.
